# 記憶壽命與存取權限：回答客戶信件

模組：memory-lifecycle（capability-architecture-interviewer，Memory 章第二個模組）
前置：memory-layer 分層表
訪談日期：2026-09-06

壽命有兩個方向。留太短，每次從零開始。留太久，過時的資訊被當成現在的事實。記憶比情境多兩個問題：誰有權看、誰有權刪。

## 診斷

### 留太久

全部記錄都沒刪過，最舊的一筆是兩年前這個案子開始的時候。

與承辦 PM 給出的半衰期對照：

| 記憶項目 | 開始不準的時間 | 現存最舊 |
|---|---|---|
| 過去做過的決定 | 一年半 | 兩年 |
| 界線判斷力 | 一年 | 兩年 |
| 客戶行為模式 | 一到兩年 | 兩年 |

三項的現存最舊記錄都已超過自己的半衰期，而且它們看起來跟昨天寫的一模一樣。

**前提已經不在、但記錄還在的項目：** 有一筆。有人引用了舊的決定，但那個決定的前提已經變了，是開會時被廠商指出來的。承辦 PM 表示其他想不到。

### 記憶的正確性目前由對方把關

兩個方向的記憶失誤，發現的人都是廠商。

該記得的沒記得，是廠商想起來的，見 memory-layer 的開場實例。
不該引用的引用了，是廠商在會議上指出來的，見本節上一段。

### 留太短

無。法規要求永久保留，所以沒有項目因為期限太短而消失。

但要註明：不在系統裡的兩項，也就是界線判斷力與客戶行為模式，實際上並沒有保存機制，它們靠人記得。這不是留太短，是根本沒有保存。現在靠什麼補上，答案是靠某個人記得，依模組規定特別標記。

### 一個做得到與做不到的落差

承辦 PM 明確表示，到期後她要的處理方式是封存並標記過期，但做不到。沒有標記機制，所有記錄看起來都一樣新。

經回報矛盾後澄清：可以手打文字註記，但沒有系統層級的過期標記。不會有欄位、不會變色、檢索時不會被過濾。也就是註記寫得下去，但不會主動攔住任何人。要看到它，前提仍是有人翻到那一筆，而 memory-layer 已確認常態是沒有人去翻。

這個缺口與 knowledge-canvas 標為最急的那一項同源：沒有任何東西能標記一筆記錄是什麼時候的、還算不算數。

## 權限盤點

| 類別 | 項目 | 說明 |
|---|---|---|
| 全公司可看 | 無 | 訪談中未出現全公司層級開放的記憶項目 |
| 限特定角色 | 過去做過的決定、XRIM 全部分頁 | 限案內成員 |
| 限特定角色，且需知道要問誰 | 界線判斷力、客戶行為模式 | 新人問得到，但要先知道問誰。這個前提本身是一道隱形的門 |
| 絕對不可進 AI | 依 knowledge-canvas，合約細節與專案資源分配及內部時程。理由是敏感 | 客戶行為模式雖未列入清單，但敏感度高，且目前不在任何系統裡 |

XRIM 的 Risk 與 Issue 於 2026-09-06 由承辦 PM 裁定為 AI 可讀，同時她也確認這部分被客戶看到會有事。兩件事並存，因此對外輸出端必須有規則攔截。

## 可追溯性檢查

本節於 2026-09-06 由承辦 PM 更正。

先前記錄為「證明不出來，只知道最後修改人」，那是把 Excel 的檔案屬性當成唯一線索。承辦 PM 更正：可追溯是可以確定的。XRIM 與 FAQ 的每一筆內容本身就明確記錄雙方同意日期、可追溯的 email date 或同意當時的 meeting 日期、以及同意人。

因此內容層可追溯：這個決定是誰、在什麼時候、根據哪封信或哪場會同意的，查得出來。

仍未確認的是事後修改。一筆記錄被寫下之後有沒有被人改過、改了什麼，本輪未取得資訊，標為未定。knowledge-canvas 記載 XRIM 與 FAQ 沒有版本號、只能看檔案修改時間，該項與本節不衝突：內容層有同意人與日期，檔案層沒有版本控管。

依模組規定記錄這一句：查不出是誰寫的、什麼時候寫的記憶，不應該被當成判斷依據。本案在內容層通過這項檢查。

而 XRIM 目前的狀態為五個條件並存：

| 條件 | 狀態 |
|---|---|
| 唯一事實來源 | 是，2026-09-06 裁定 |
| AI 可讀 | 是，2026-09-06 裁定 |
| 內容層可追溯，含同意人與同意日期 | 是，2026-09-06 更正 |
| 事後是否被修改可查 | 未定 |
| 可標記過期 | 否 |
| 有人會回頭看 | 否，常態是不會 |

本模組不改動承辦 PM 的裁定，僅照實記錄各條件的狀態。

## 同意記錄的檢查

會議發言會被記進 decision，而且大家都知道會被記。這一項沒有同意問題。

客戶行為模式沒有記在任何系統，只在腦中，所以不會流出去。

由此產生一個兩難，本模組不代為解決：

**這一項現在的安全來自它沒有被記錄。** 一旦寫下來讓新人接得住，它就同時變成一份被本人看到會更糟的文件。也就是說，可交接與可保密在這一項上互相衝突。

前面各章對腦中知識的建議都是寫下來，唯獨這一項不能照樣建議。

## 缺口

這一輪最模糊的有兩處。

第一，一筆記錄被寫下之後有沒有被事後修改，以及改了什麼，本輪未問到。內容層的同意人與同意日期是可追溯的，但修改軌跡未確認。

第二，那三個半衰期數字的來源。

承辦 PM 給出一年半、一年、一到兩年三個數字，但訪談沒有取得這些數字的依據，也就是它們是根據實際案例推得，還是憑感覺。

導致的後果：memory-governance 模組要訂定期審查的週期，會直接引用這三個數字。若它們只是憑感覺，審查週期就建立在未經驗證的基礎上。這一格標為未定，不代為推定。

## 給實作的建議

### 最該補的一件事仍然是標記

承辦 PM 自己要的處理方式就是封存並標記過期，卡的是工具不是意願。這與 knowledge-canvas 標為最急的 XRIM 版本號是同一件事的兩面。一個解法可以同時處理兩個模組的最高優先項。

### 三個半衰期可以直接變成規則

一年半、一年、一到兩年這三個數字，目前沒有寫在任何地方。即使沒有系統標記，把它們寫成引用規則也有效，因為它讓引用者知道要問一句「這筆多久了」。

### 客戶行為模式這一項，建議不要落成文件

理由是承辦 PM 自己講的兩句話：被本人看到更糟，以及它現在的安全來自沒有被記錄。若要交接，建議走口頭交接，這也是現況。本模組不建議改變它。
