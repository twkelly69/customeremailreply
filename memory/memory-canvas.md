## 診斷

### 三層歸屬對帳的結果

判準由模組定義，選擇由承辦 PM 做出，引擎未代選。判準為：每次都一樣歸 Knowledge，每次都不同歸 Context，過去發生過且會累積歸 Memory。

| 編號 | 項目 | 裁定 | 另外兩張要拿掉的部分 |
|---|---|---|---|
| A1 | XRIM 的 decision | Knowledge | Context Canvas 與 Memory Canvas 不再各自維護，Context 的情境規則第三條改為引用 Knowledge |
| A2 | FAQ | Knowledge | Memory Canvas 拿掉 |
| A3 | 合約 | 分開處理。合約文件本身留在 Knowledge，各客戶合約實際做過或擋過什麼的判例累積歸 Memory | Context 第 13 項改為引用 Knowledge |
| B | CRA visit 時間不固定 | Context | Memory Canvas 拿掉，併入 Context 第 10 項 |
| C | 報價邏輯與內部立場 | Context | Knowledge Canvas 的未定案清單保留該項為未定案，但歸屬改為 Context |
| D | 第 5 項主題判斷 | 不納入 Memory。本來就該每次重新產生，不需要累積 | 維持只在 Context |
| E | FAQ 更新頻率的矛盾 | 不定期，問題答案確認後才更新 | memory-update 已回沖，與 knowledge-canvas 一致 |

B 與 C 兩項原本被當成 Memory 或 Knowledge，經裁定後都移往 Context。依模組的警告，這兩類錯置分別會導致：某一次的說法被當成公司政策，以及某個客戶的特例被套用到所有人。本案在裁定後兩者皆已避免。

E 這一項要記錄一次答案反覆。同一日承辦 PM 先答定時更新，對帳時改答不定期。本檔採用後者。

### 壓力測試四題的結果

一，同一個人第二次來。Memory 給不出來，要花力氣挖，而且通常挖得到結論、挖不到理由。

這句收攏了兩個先前的發現：大部分只寫結論不寫理由，以及裁決權給了最簡略的 XRIM。

二，新人讀完三張 Canvas。做不到，缺最多的是 Memory，因為 Memory 的內容大部分不在文件裡。

與第一題是同一件事的兩面：**Memory 這一層目前有結構、沒內容。** 四個模組把形狀盤清楚了，誰寫、誰審、誰刪、保存多久都有答案，但內容仍在承辦 PM 腦中。

三，改一個政策要改幾個地方。三個地方，也就是 SOP、FAQ、以及在 XRIM 開新的 decision 說明改變。舊 decision 不會動。

依模組規定指出該分而未分之處：舊 decision 不會動，而 closed 的 decision 照樣會被引用，且沒有過期標記。因此政策改變後，XRIM 裡會同時存在兩套說法，外觀完全一樣，要靠引用的人自己看日期判斷。這不是三個地方要改的問題，是第四個地方沒有被處理。

四，AI 講錯一件事能否分辨是哪一層。分得出來，因為承辦 PM 知道正確答案為何，但要花時間去追是哪裡來的。

照實標記：這個能力綁在承辦 PM 知道正確答案這件事上，不在系統上。換一個不知道正確答案的人，三種錯誤看起來就都一樣了。

## 缺口

這一輪最模糊的是區塊 2 的保存期限欄，六項中有四項未定。

原因照實記錄：這四項目前都不在任何系統裡，沒有被設過期限，訪談中也未取得數字。只有承辦 PM 先前給過半衰期的兩項有值。

導致的後果：Memory 這一層無法排出「哪些必須即時取得、哪些可以沿用」的時機表，而 Context 章能排出來。這是三層之中唯一缺這張表的一層。

第二個缺口延續 memory-governance：三項只能加不能減的記憶，缺的是一個能標記「這個決定已經不算數」的機制。壓力測試第三題證實了它的實際後果，也就是政策改變後兩套說法並存。

## 給實作的建議

### 三層之中，Memory 是唯一有結構沒內容的一層

Knowledge 有文件、Context 有系統與來信，Memory 的六項裡有五項沒有寫入者。因此這一層的下一步不是設計流程，而是把內容寫下來。

例外是客戶行為模式，承辦 PM 已決定不落成文件，本建議不涵蓋該項。

### 優先寫下來的兩筆，都走既有的 XRIM risk

第一筆，這個案子拿不到可靠的 kit 效期資料。它每月造成 30 分鐘的重複說明。
第二筆，換整組 kits 是更安全的選項。它同時是回寫斷點與對外斷點。

兩筆都符合 memory-update 的最小可行流程限制，不新增系統、不新增會議、只新增承辦 PM 一個動作。

### 理由欄位仍是最划算的一項

壓力測試第一題確認挖得到結論、挖不到理由，而理由缺席的成本已量化為每半年一場會議。要求 decision 補上為什麼，不新增系統也不新增人力。

### 三個模組指向同一個解法

knowledge-canvas 的 XRIM 缺版本號、memory-lifecycle 的想封存卻做不到、memory-governance 的只能 close 沒有作廢，是同一件事的三個面向。壓力測試第三題提供了第四個佐證。

## 不可寫入本檔的內容

逐條列出，句子可判斷。

1. 不得寫入對特定客戶或個人的行為評價。判斷方式：檢查是否出現某方會用某理由推責任這類敘述。
2. 不得寫入合約金額、客戶名、服務細節、保密條款。判斷方式：檢查是否出現金額數字、客戶全名、合約條款編號。
3. 不得寫入專案資源分配與內部時程。判斷方式：檢查是否出現人力配置或內部里程碑日期。
4. 不得寫入僅存在於 XRIM Risk 或 Issue 分頁的內容。判斷方式：檢查該敘述是否只能從 Risk 或 Issue 取得。
5. 不得以肯定句陳述四項未定案判準。判斷方式：檢查是否出現新需求與改善需求界線、微調與額外工作界線、scope in 與 out 標準、報價邏輯的肯定式定義。

## 記憶規則

以下三條可直接貼進專案 CLAUDE.md。

一，什麼情況應該把一個決定寫進 memory：當它是「這個案子有什麼靠不住」這一類的認識時，例如某個資源拿不到、某個機制時間不固定、某個做法試過不行。這一類寫成一筆 risk 進 XRIM，走既有的 review 程序。什麼情況不應該：每次都會重新產生的判斷不寫，例如這封信真正的主題；對特定人或客戶的行為評價不寫，理由見不可寫入清單第一條。

二，引用任何 decision 之前，必須確認兩件事：一是該筆是否為最新版本，二是它的前提是否仍然成立。closed 只代表這件事處理完了，不代表決定失效。決定的參考效期約一年半，超過即不得直接引用。

三，寫入 decision 時必須同時記錄為什麼，不只記錄做了什麼。理由缺席會導致同一個議題被重複討論，本案已量化為每半年一場會議。
